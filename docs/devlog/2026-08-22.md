# 개발 기록 — 2026-08-22

## 오늘 목표

fullscreen 게임에 포커스가 있을 때 단독 F키가 기존 `WM_HOTKEY` 경로로 들어오지 않는 문제를 보완하고, 단축키 입력 창의 글자 잘림을 수정한다.

## 진행한 내용

* 기존 수동 테스트에서 Whale 전역 단축키가 동작하는 것을 확인했다.
* SuddenAttack 앱별 음소거 자체와 `Ctrl + Alt + F8`은 게임에 포커스가 있을 때도 동작했다.
* 단독 `F8`은 Alt+Tab으로 일반 Windows 창에 나온 뒤에는 동작했지만, SuddenAttack이 foreground일 때는 기존 `RegisterHotKey`/`WM_HOTKEY` 경로로 들어오지 않았다.
* modifier가 포함된 단축키는 기존 `RegisterHotKey` 방식을 유지하고, 단독 F1~F11만 Raw Input으로 받도록 `HotkeyService`를 확장했다.
* keyboard top-level collection인 Usage Page `0x01`, Usage `0x06`을 기존 MutePilot window handle에 `RIDEV_INPUTSINK`로 한 번 등록했다.
* `WM_INPUT`에서 `RAWKEYBOARD`를 읽고 현재 설정된 단독 F키와 일치하는 경우에만 기존 mute action을 호출하도록 했다.
* key-down에서 한 번만 실행하고 key-up에서 눌림 상태를 해제해 keyboard auto-repeat가 연속 토글로 이어지지 않게 했다.
* 단독 F키와 modifier 조합을 동시에 등록하지 않도록 경로를 나눴고, MutePilot 내부 중복 검사도 그대로 유지했다.
* 단축키 입력 창을 조금 키우고 표시 상자의 `MinHeight`, padding, 가로·세로 중앙 정렬을 조정했다. 게임에도 F키 입력이 함께 전달될 수 있다는 안내와 modifier 조합 안내도 추가했다.

## 새롭게 알게 된 내용

* `RegisterHotKey`와 `WM_HOTKEY`는 Windows가 등록을 받아 전달하는 전역 단축키 경로이고, Raw Input은 등록한 장치의 입력 정보를 직접 `WM_INPUT`으로 받는 별도 경로다.
* `RIDEV_INPUTSINK`와 대상 window handle을 사용하면 MutePilot이 foreground가 아닐 때도 등록한 keyboard raw input을 받을 수 있다.
* Raw Input을 받는다고 해서 모든 키를 기록할 필요는 없다. 이번 구현은 설정된 단독 F1~F11과 modifier의 현재 눌림 상태만 확인하며 일반 키 입력, 문자열, 입력 이력은 저장하거나 전송하지 않는다.
* `RIDEV_NOLEGACY`를 사용하지 않았기 때문에 F키 입력은 foreground 프로그램에도 계속 전달된다.

## 문제와 해결

SuddenAttack 자체의 오디오 session 제어는 정상이었지만 단독 `F8`만 게임 foreground에서 전달되지 않았다. `Ctrl + Alt + F8`은 같은 상황에서 동작했으므로 오디오 로직을 바꾸지 않고 단독 F키의 입력 경로만 Raw Input으로 보완했다. keyboard hook, 입력 주입, game process 접근, anti-cheat 연동은 사용하지 않았다.

기존 단축키 입력 창은 어두운 표시 상자 안의 조합 문자열이 세로로 잘려 보였다. 창과 표시 영역에 충분한 높이와 padding을 주고 text alignment를 중앙으로 맞췄다.

## 확인 결과

* `dotnet restore MutePilot.sln`: 성공
* `dotnet build MutePilot.sln`: 성공, 경고 0개, 오류 0개
* 경로 분리: 단독 `F8`은 Raw Input, `Ctrl + F8`은 기존 `RegisterHotKey` 경로를 사용하는 것을 확인했다. F12 거부도 유지됐다.
* GUI 실행: 성공. `Master Audio`, `Applications`, 단축키 입력 창이 정상적으로 열렸다.
* Raw Input 초기화: 성공. 시작 시 `RegisterRawInputDevices` 실패 안내가 없었고 기존에 저장된 단독 `F8` 바인딩도 형식 변경 없이 복원됐다.
* 입력 창: 현재 Windows DPI 100%에서 `현재: F8` 문구가 잘리지 않고 표시 영역 중앙에 보이는 것을 창 렌더링으로 확인했다. 125%, 150%는 실제 display scaling 변경 테스트가 남아 있다.
* 자동 검증 중에는 단축키를 누르거나 master/application mute 상태를 변경하지 않았다.
* 개선 후 SuddenAttack foreground에서 단독 `F8`이 실제로 동작하는지는 아직 수동 검증하지 않았다.

## 단독 F키 polling 방식 재개선

### 진행한 내용

* Raw Input 적용 후 다시 테스트했지만 단독 `F8`은 SuddenAttack 밖에서만 동작하고 게임 foreground에서는 계속 들어오지 않았다.
* Master Audio에 지정한 단독 `F7`도 같은 결과였고, `Ctrl + Alt + F8`은 SuddenAttack foreground에서 계속 정상 동작했다.
* 앱별·master mute 로직과 Raw Input 반복 방지는 정상이라서 오디오 코드는 바꾸지 않았다.
* 단독 F1~F11의 Raw Input trigger를 제거하고 `GetAsyncKeyState` polling으로 교체했다. modifier 조합은 기존 `RegisterHotKey`/`WM_HOTKEY` 경로를 유지했다.
* 15ms 간격의 background task 하나가 현재 설정된 단독 F키의 virtual-key만 확인한다. 설정되지 않은 영문, 숫자, 기타 키는 조회하지 않는다.
* key state의 high-order bit만 사용하고 `UP → DOWN`에서 한 번 실행한 뒤 key-up을 볼 때까지 latch를 유지하도록 했다.
* poller에서 감지한 action은 WPF `Dispatcher`로 넘겨 UI thread에서 기존 mute 흐름과 화면 갱신을 실행하도록 했다.
* 앱 종료 시 cancellation을 요청하고 polling task가 끝난 뒤 기존 native hotkey와 message hook을 정리하도록 했다.

### 새롭게 알게 된 내용

* `GetAsyncKeyState` 반환값의 high-order bit는 현재 key-down 상태를 뜻한다. low-order bit는 다른 process와 호출 시점에 영향을 받아 신뢰할 수 없으므로 사용하지 않았다.
* polling은 event history를 모으는 방식이 아니라 현재 상태를 짧은 간격으로 확인하는 방식이라서 별도 latch가 있어야 한 번 누를 때 한 번만 동작한다.
* foreground 프로그램이 더 높은 권한으로 실행되면 UIPI 때문에 `GetAsyncKeyState`가 0을 반환할 수 있다. MutePilot이 자동으로 관리자 권한을 요구하게 만들지는 않았고, 필요할 때 같은 권한 수준에서 수동 확인하기로 했다.

### 문제와 해결

keyboard Raw Input을 `RIDEV_INPUTSINK`로 등록해도 SuddenAttack foreground에서는 단독 F7/F8을 받지 못했다. game-specific 접근이나 keyboard hook을 추가하지 않고, 구성된 F키 상태만 확인하는 작은 polling 경로로 교체했다.

poller가 UI를 막거나 key마다 thread를 만들지 않도록 `PeriodicTimer`를 사용하는 background task 하나로 구성했다. 설정 변경과 polling이 같은 binding 상태를 볼 수 있도록 작은 lock 범위도 추가했다.

### 확인 결과

* `dotnet restore MutePilot.sln`: 성공
* `dotnet build MutePilot.sln`: 성공, 경고 0개, 오류 0개
* 반복 상태 검증: `UP, DOWN, DOWN, DOWN, UP, DOWN, UP` 순서에서 두 번의 `UP → DOWN`만 trigger되는 것을 실제 key 입력 없이 확인했다.
* GUI 실행: 성공. Master Audio 상태와 Applications 영역, 기존 단독 F키 설정이 로드됐다.
* poller 초기화: 성공. 초기화 실패 안내가 없었고 5초 idle 측정에서 추가 CPU 시간이 관찰되지 않았다.
* 설정 호환성: `%LocalAppData%\MutePilot\settings.json` schema를 바꾸지 않았고 실행 전후 파일 수정 시간도 그대로였다.
* 종료 처리: 창을 닫은 뒤 polling task를 정리하고 process가 정상 종료되는 것을 확인했다.
* source에서 Raw Input API를 제거했고 keyboard hook, 입력 주입, game process 접근, 일반 key logging은 추가하지 않았다.
* polling 적용 후 SuddenAttack foreground의 단독 F7/F8 실제 동작은 아직 수동 검증하지 않았다.

### 다음 목표

SuddenAttack foreground에서 단독 F7/F8을 다시 수동 검증하고, 게임이 관리자 권한으로 실행 중이라면 동일한 권한 수준이 필요한지도 확인한다.

## 선택형 음소거 상태 오버레이 (초기 팝업형)

### 오늘 목표

게임이나 작업 중 MutePilot 메인 창을 다시 열지 않아도 방금 실행한 음소거 대상과 결과를 짧게 확인할 수 있는 상태 오버레이를 만든다.

### 구현한 내용

* 마스터·앱별 버튼과 전역 단축키로 음소거 전환이 성공했을 때 대상 이름과 `음소거` 또는 `음소거 해제` 상태를 표시하도록 했다.
* 오버레이는 주 모니터 작업 영역의 오른쪽 위에 약 1.5초 동안 나타나는 별도의 작은 WPF 창으로 만들었다.
* 새 상태가 들어오면 같은 창의 내용을 바꾸고 자동 숨김 시간을 처음부터 다시 시작한다.
* `WS_EX_NOACTIVATE`, `WS_EX_TRANSPARENT`, `WS_EX_TOOLWINDOW` 확장 스타일을 적용해 포커스를 가져가지 않고 마우스 클릭이 통과하며 작업 표시줄에도 나타나지 않게 했다.
* 메인 화면에 기본값 ON인 `오버레이` 설정을 추가했다. OFF로 바꾸면 표시 중인 창도 즉시 숨긴다.
* 설정을 `%LocalAppData%\MutePilot\settings.json`의 `overlayEnabled`에 저장하고 다시 실행할 때 복원한다. 이 항목이 없는 기존 설정 파일은 ON으로 읽어 기존 단축키 설정과 호환되게 했다.
* 오버레이는 게임 프로세스 주입이나 렌더링 hook 없이 MutePilot 프로세스의 독립된 WPF 창으로만 동작한다.

### 새롭게 알게 된 내용

* WPF의 `Topmost`와 `ShowActivated=false`만으로 기본 동작을 정하고, Win32 extended window style을 함께 적용하면 보조 상태 창이 사용자 입력 흐름을 방해하지 않게 만들 수 있다.
* 같은 `DispatcherTimer`를 멈췄다가 다시 시작하면 빠르게 상태가 연속으로 바뀌어도 마지막 알림이 정해진 시간 동안 보이게 할 수 있다.
* JSON model의 bool property에 기본값을 지정하면 이전 설정 파일에 새 field가 없어도 자연스럽게 기본 동작을 적용할 수 있다.
* 일반 topmost 창은 독점 전체 화면 렌더링 위에 항상 표시된다고 보장할 수 없다. 이번 기능은 windowed 또는 borderless 환경을 기준으로 하고 이 제한을 문서에 남겼다.

### 문제와 해결

처음에는 `Window.ShowActivated`를 override하려 했지만 virtual property가 아니어서 빌드 오류가 발생했다. XAML에서 `ShowActivated="False"`를 지정하고 native extended style을 적용하는 방식으로 고쳤다.

독립 오버레이 검증 도구를 Windows PowerShell 5.1에서 실행했을 때 .NET 8 assembly를 불러오지 못했다. 같은 스크립트를 .NET 8을 사용하는 `pwsh -STA`에서 실행해 WPF 창의 실제 속성과 숨김 동작을 확인했다.

### 확인 결과

* `dotnet restore MutePilot.sln`: 성공
* `dotnet build MutePilot.sln`: 성공, 경고 0개, 오류 0개
* 실제 WPF 오버레이 창에서 주 모니터 오른쪽 위 배치와 상태 문구 렌더링을 확인했다.
* 표시 전후 foreground window가 바뀌지 않았고, `WS_EX_NOACTIVATE`, `WS_EX_TRANSPARENT`, `WS_EX_TOOLWINDOW`가 실제 window handle에 적용된 것을 확인했다.
* 약 1.5초 뒤 자동으로 숨겨지고, 중간에 새 상태를 표시하면 timeout이 다시 시작되는 것을 확인했다.
* OFF 전환 시 표시 중인 창이 즉시 숨고, OFF 상태에서는 새 표시 요청이 나오지 않는 것을 확인했다.
* 실제 메인 화면에서 ON/OFF를 바꾸고 프로그램을 다시 실행해 `overlayEnabled` 값과 UI가 함께 복원되는 것을 확인했다.
* 기존 마스터·앱 목록과 hotkey 설정이 그대로 불러와지는 것을 확인했다.
* 자동 검증 중에는 master 또는 application의 실제 음소거 상태를 변경하지 않았다.
* SuddenAttack을 foreground로 둔 상태의 오버레이 표시는 아직 수동 검증하지 않았다.

### 다음 목표

SuddenAttack의 실제 windowed 또는 borderless 환경에서 오버레이 표시를 수동 확인하고, 시스템 트레이와 Windows 시작 시 실행 기능을 검토한다.

## 고정형 compact HUD로 개선

### 오늘 목표

음소거를 바꿀 때만 잠깐 나타나던 오버레이를, 현재 상태를 계속 확인할 수 있는 작고 고정된 HUD로 바꾼다. 기존 카드는 알림으로는 동작했지만 크기가 크고 곧 사라져 게임 중 상태를 다시 확인하기 어려웠다.

### 구현한 내용

* 오버레이 ON 상태에서는 HUD가 계속 보이고, OFF로 바꾸면 즉시 완전히 숨도록 자동 숨김 timer를 제거했다.
* HUD 폭을 226px로 줄이고 큰 아이콘 영역과 넓은 padding을 없앴다. 작은 제목 아래에 한 줄 높이 23px인 상태 행을 배치했다.
* `Master`는 항상 첫 행에 표시하고, 앱 행은 모든 활성 오디오 session이 아니라 사용자가 저장한 단축키 바인딩만 사용했다.
* 저장된 앱에 활성 오디오 session이 있으면 `음소거`, `음소거 해제`, `일부 음소거`를 표시하고, session이 없으면 `실행 안 됨`으로 남겨 뒀다.
* 앱 바인딩이 많아도 HUD가 지나치게 길어지지 않도록 최대 7개 앱을 표시하고 나머지는 `외 N개`로 줄였다.
* 마스터·앱별 버튼, 전역 단축키, 앱 목록 새로고침, 단축키 설정·삭제 뒤에 같은 HUD window의 전체 상태 snapshot을 갱신하도록 연결했다.
* 오버레이가 켜져 있을 때 2초 간격으로 상태를 비동기 조회해 저장 앱의 오디오 session 시작·종료도 반영한다. 조회 중 사용자가 음소거를 바꾼 경우에는 이전 조회 결과가 새 상태를 덮지 않도록 revision을 비교했다.
* 기존 `overlayEnabled` 설정과 단축키 저장 형식은 바꾸지 않았다. ON으로 바꾸면 현재 snapshot을 즉시 표시하고 최신 상태를 다시 조회한다.

### 이렇게 구성한 이유

활성 오디오 session을 전부 HUD에 복사하면 브라우저나 임시 프로그램이 실행될 때마다 목록 높이와 순서가 바뀐다. 사용자가 직접 단축키를 저장한 앱만 표시하면 HUD가 작고 예측 가능한 상태로 유지되고, 앱이 꺼져 있어도 다음에 사용할 대상을 확인할 수 있다.

HUD는 계속 독립된 일반 WPF window로 동작한다. 게임 프로세스 주입, DirectX/OpenGL hook, 입력 주입은 사용하지 않았다. 일반 창과 borderless/windowed 게임에서는 표시를 기대할 수 있지만 독점 전체 화면에서는 Windows와 게임 렌더링 방식에 따라 보이지 않을 수 있다는 제한도 그대로다.

### 확인 결과

* `dotnet restore MutePilot.sln`: 성공
* `dotnet build MutePilot.sln`: 성공, 경고 0개, 오류 0개
* 실제 앱을 실행해 메인 GUI, 226×94px HUD, `Master`와 저장된 `suddenattack` 행이 함께 표시되는 것을 확인했다.
* 2.3초 동안 기다린 뒤에도 HUD가 자동으로 숨지 않고 계속 표시됐다.
* 실제 window handle에서 `WS_EX_NOACTIVATE`, `WS_EX_TRANSPARENT`, `WS_EX_TOOLWINDOW`가 유지되고 foreground window가 바뀌지 않는 것을 확인했다.
* OFF로 바꾸면 HUD가 즉시 사라지고 `overlayEnabled: false`가 저장됐다. 다시 ON으로 바꾸면 바로 나타났고 프로그램 재시작 뒤에도 ON과 HUD가 복원됐다.
* 기존 master hotkey와 앱 바인딩 내용은 ON/OFF 및 재시작 검증 전후에 그대로 유지됐다.
* 실제 음소거를 바꾸지 않는 별도 snapshot 검증에서 같은 HUD window 한 개의 Master 행이 `음소거 해제`에서 `음소거`로 갱신됐다.
* 사용자는 이전 팝업형 오버레이가 SuddenAttack에서 동작하는 것을 확인했다.

### 게임 수동 확인 결과

* 실제 SuddenAttack에 포커스가 있는 동안 고정형 compact HUD가 사라지지 않고 계속 표시됐다.
* 메인 화면에서 Overlay를 ON으로 바꾸면 HUD가 나타나고, OFF로 바꾸면 즉시 숨었다.
* SuddenAttack에 설정한 기존 단독 `F8`로 앱별 음소거와 음소거 해제가 계속 정상 동작했다.
* 고정형 HUD로 변경한 뒤에도 실제 게임 환경에서 상태 표시와 기존 단축키 기능을 함께 사용할 수 있음을 확인했다.
* 이 결과는 SuddenAttack에서 확인한 내용이며, 모든 독점 전체 화면 애플리케이션에서 일반 WPF overlay 표시를 보장한다는 뜻은 아니다.

## 오버레이 위치·잠금·투명도 설정

### 오늘 목표

고정형 HUD가 게임 안에서 잘 보이는 것을 확인했으므로, 사용자가 모니터 구성과 화면 배치에 맞춰 위치와 투명도를 직접 정할 수 있게 한다. 게임 중에는 설정 control이 mouse 입력을 가로채지 않도록 자동으로 표시 전용 상태로 바꾼다.

### 구현한 내용

* 기존 click-through HUD에 작은 잠금 버튼을 추가했다. 기본값은 기존 동작과 가까운 잠금 상태다.
* 잠금을 풀면 제목 영역의 WPF `Thumb`을 drag해 위치를 옮길 수 있고, drag 완료 시점의 `Left`, `Top`을 저장한다.
* 잠금 해제 상태에만 20~100% 투명도 slider를 표시한다. 상태 card에만 opacity를 적용해 slider와 잠금 control은 읽고 조작하기 쉽게 유지했다.
* `overlayLocked`, `overlayOpacity`, `overlayLeft`, `overlayTop`을 기존 `%LocalAppData%\MutePilot\settings.json`에 추가했다. 기존 hotkey와 `overlayEnabled` 구조는 바꾸지 않았다.
* 저장 좌표가 연결된 monitor의 작업 영역을 벗어나면 `MonitorFromPoint`와 `GetMonitorInfo`로 가장 가까운 화면 안에 HUD 전체가 남도록 좌표를 제한했다.
* 메인 화면에 `오버레이 위치 초기화` 버튼을 추가해 저장 좌표를 지우고 주 모니터 오른쪽 위로 바로 되돌릴 수 있게 했다.
* 약 400ms 간격의 `DispatcherTimer` 하나가 generic Windows foreground window 정보를 확인한다. `GetForegroundWindow`로 가져온 창이 자기 monitor 전체를 덮으면 fullscreen display-only 상태로 본다.
* fullscreen 중에는 사용자의 저장된 잠금 설정과 투명도를 수정하지 않고 잠금 버튼과 slider를 숨긴다. HUD window에 `WS_EX_TRANSPARENT`를 적용해 모든 mouse 입력이 foreground 앱으로 통과하게 했다.
* 일반 화면으로 돌아오면 fullscreen 강제 상태만 해제하고 사용자가 저장한 잠금 또는 잠금 해제 상태를 다시 적용한다.
* 일반 화면에서 잠긴 HUD는 `WM_NCHITTEST` 결과를 본문에는 `HTTRANSPARENT`, 잠금 버튼에는 `HTCLIENT`로 나눠 본문은 방해하지 않으면서 다시 잠금을 풀 수 있게 했다.

### 이렇게 구성한 이유

SuddenAttack process 이름을 확인하거나 게임 내부 렌더링에 접근하면 다른 프로그램에 적용하기 어렵고 안전 범위도 벗어난다. 이번 감지는 process 이름과 관계없이 foreground window rectangle과 monitor rectangle만 비교한다. 게임 memory, anti-cheat, DirectX/OpenGL, 입력 주입은 사용하지 않았다.

fullscreen display-only는 사용자의 잠금 선택과 별도 runtime 상태로 두었다. 사용자가 잠금을 풀어 둔 채 게임으로 돌아가도 설정 파일을 `locked`로 덮어쓰지 않으므로 Alt+Tab 뒤에는 원래 설정 화면이 다시 나타난다.

### 문제와 해결

잠금 상태에서 window 전체에 `WS_EX_TRANSPARENT`를 계속 적용하면 잠금 버튼까지 누를 수 없었다. 일반 화면에서는 native style의 click-through를 해제하고 `WM_NCHITTEST`에서 본문과 버튼 hit 영역을 나누는 방식으로 해결했다. fullscreen에서는 control 자체를 숨기고 window 전체 click-through를 다시 강제한다.

자동 검증용 fullscreen 창은 Windows foreground 제한 때문에 실제 focus를 가져오지 못한 경우가 있었다. fullscreen detector를 interface로 분리한 구조를 이용해 controllable 상태를 넣고 실제 400ms timer의 display-only 전환과 복귀를 먼저 확인했다. 이후 실제 SuddenAttack에서도 같은 전환과 입력 차단을 수동 확인했다.

### 확인 결과

* `dotnet restore MutePilot.sln`: 성공
* `dotnet build MutePilot.sln`: 성공, 경고 0개, 오류 0개
* 실제 앱 GUI와 기존 저장 앱 바인딩, persistent HUD가 정상적으로 불러와졌다.
* 잠금 해제 상태에서 drag delta만큼 HUD가 이동했고 drag 완료 좌표가 설정 event로 전달됐다. 잠근 뒤에는 같은 drag event로 위치가 바뀌지 않았다.
* 잠긴 HUD 본문은 click-through였고 잠금 버튼 영역만 click target으로 남는 것을 native hit test로 확인했다.
* 투명도 20%와 100%가 상태 card에 적용됐고, 범위를 벗어난 저장 값은 각각 20%와 100%로 제한됐다.
* `(180, 140)` 위치를 저장한 뒤 두 번 실행해 같은 좌표가 복원되는 것을 확인했다.
* 매우 큰 양수·음수 좌표는 현재 monitor 작업 영역 안으로 복구됐다.
* 메인 화면의 위치 초기화 뒤 좌표가 기본값으로 저장되고 HUD가 주 모니터 오른쪽 위로 돌아갔다.
* Overlay OFF에서 즉시 숨고 ON에서 다시 나타나는 기존 동작을 확인했다.
* controllable fullscreen state에서 400ms monitor가 display-only를 켜고 control을 숨겼으며, 일반 상태로 돌아오자 이전 잠금 해제 UI와 70% opacity가 복원됐다.
* overlay window를 표시하고 상태를 바꾸는 동안 기존 foreground window가 바뀌지 않았다.
* 기존 master hotkey와 앱별 바인딩은 설정·재시작 검증 전후에 그대로 유지됐다.
* 실제 PC에서 잠금을 풀었을 때 HUD를 drag해 위치를 바꿀 수 있었고, 잠근 뒤에는 drag할 수 없었다.
* 투명도 slider와 위치 초기화가 정상 동작했다. 위치, 투명도, 잠금 상태는 앱을 다시 실행한 뒤에도 그대로 복원됐다.
* SuddenAttack이 foreground/fullscreen일 때 HUD가 자동으로 display-only·click-through 상태가 되어 게임 중에는 위치나 설정을 실수로 바꿀 수 없었다.
* Alt+Tab으로 게임 밖에 나온 뒤에는 저장된 잠금 상태에 맞춰 HUD 설정 기능을 다시 사용할 수 있었다.
* 기존 SuddenAttack 단독 `F8` 음소거와 Overlay ON/OFF도 계속 정상 동작했다.

## 시스템 트레이 백그라운드 동작

### 오늘 목표

메인 창을 계속 띄워 두지 않아도 단축키와 오버레이를 사용할 수 있도록 X 버튼은 창만 숨기고, 실제 종료는 시스템 트레이에서 명확히 선택하는 구조를 만든다.

### 구현한 내용

* 별도 package 없이 .NET의 `System.Windows.Forms.NotifyIcon`과 임시 `SystemIcons.Application` icon을 사용했다.
* 트레이 메뉴에 `MutePilot 열기`, 현재 상태에 맞는 `오버레이 켜기` 또는 `오버레이 끄기`, `종료`를 추가했다. icon double-click도 열기와 같은 동작을 한다.
* `MainWindow.OnClosing`에서 실제 종료 요청이 아니면 close를 취소하고 창만 숨긴다. 처음 X를 누른 경우에만 `MutePilot이 트레이에서 계속 실행 중입니다.` 알림을 요청한다.
* 앱의 `ShutdownMode`를 `OnExplicitShutdown`으로 바꿨다. 트레이의 `종료`가 내부 flag를 설정한 뒤 정상 WPF shutdown을 요청하므로 close-to-tray 처리와 종료 처리가 서로 반복되지 않는다.
* 창을 다시 열 때 새 `MainWindow`를 만들지 않고 숨겨 둔 같은 instance를 `Show`, `Normal` 복원, `Activate` 순서로 다시 표시한다.
* `AudioService`, `HotkeyService`, 단독 F키 polling, overlay service와 두 timer는 창을 숨길 때 dispose하지 않는다. 실제 종료 시 기존 `OnClosed` 경로에서 hotkey hook과 polling, fullscreen monitor, overlay window를 정리하고 마지막에 NotifyIcon을 dispose한다.
* 메인 화면과 트레이의 오버레이 변경이 같은 `SetOverlayEnabled` 경로를 사용하도록 정리했다. 기존 `overlayEnabled`를 저장하고 HUD와 양쪽 표시를 함께 바꾸며 새 tray 전용 설정은 추가하지 않았다.

### 배운 점

`NotifyIcon`은 WPF window와 수명이 자동으로 연결되지 않는다. icon을 한 번만 만들고 실제 종료 때 `Visible`을 false로 바꾼 뒤 dispose해야 알림 영역에 오래 남는 icon을 피할 수 있다.

WPF의 기본 shutdown 조건은 열려 있는 window 수에 영향을 받는다. 메인 창을 숨기고 overlay window는 계속 쓰는 앱에서는 `OnExplicitShutdown`과 실제 종료 flag를 함께 두는 편이 종료 의도를 분명하게 만든다.

### 문제와 해결

WPF project에 Windows Forms 지원을 켜자 implicit `System.Windows.Forms`와 `System.Drawing` namespace가 WPF의 `Application`, `Button`, `Brush` 같은 이름과 충돌했다. project의 implicit using 목록에서 두 namespace만 빼고 `TrayService` 파일에서 필요한 type을 직접 import해 기존 WPF 코드를 바꾸지 않고 해결했다.

키보드 입력으로 tray menu를 반복 자동 선택할 때 이전 선택 위치가 남아 두 번째 오버레이 전환이 실행되지 않았다. 실제 menu의 접근성 tree에서 항목 이름을 확인하고 해당 항목의 기본 동작을 호출해 OFF와 ON을 각각 검증한 뒤 원래 ON 설정으로 돌려놓았다.

### 확인 결과

* `dotnet restore MutePilot.sln`: 성공
* `dotnet build MutePilot.sln`: 성공, 경고 0개, 오류 0개
* 앱 실행 후 `MainWindow`와 NotifyIcon 한 개, 기존 overlay window가 표시되는 것을 확인했다.
* X close message 뒤 메인 창만 숨고 process, tray icon, Overlay ON 상태의 HUD가 계속 남았다.
* `MutePilot 열기`와 tray icon double-click이 숨기기 전과 같은 window handle의 메인 창을 복원했다.
* 세 번 연속 숨김·복원을 반복해도 main window, NotifyIcon, menu, overlay service가 추가로 만들어지지 않았다.
* 트레이에서 오버레이를 OFF로 바꾸자 `settings.json`, HUD, 메인 화면 버튼이 함께 OFF가 됐다. 다시 ON으로 바꿔 세 항목이 함께 복원되는 것을 확인했다.
* 트레이 `종료` 뒤 main, overlay, NotifyIcon window가 모두 없어지고 process가 종료됐다. 이후 앱을 다시 실행해 NotifyIcon이 한 개만 생기고 정상 종료되는 것도 확인했다.
* 자동 검증 중에는 master 또는 application mute hotkey를 누르지 않아 사용자의 실제 audio 상태를 바꾸지 않았다.
* 기존 master hotkey, application binding, `overlayEnabled`, `overlayLocked`, `overlayOpacity`, `overlayLeft`, `overlayTop` 설정 구조는 변경하지 않았다.

### 실제 PC 수동 확인 결과

* X 버튼을 누르면 `MainWindow`만 숨고 MutePilot process와 tray icon은 계속 유지됐다.
* 메인 창을 숨긴 동안에도 persistent HUD가 보였고 audio 상태 변경이 계속 반영됐다.
* 같은 상태에서 SuddenAttack 단독 `F8` 음소거와 음소거 해제가 정상 동작했다.
* Tray icon double-click으로 숨겨 둔 기존 `MainWindow`가 다시 나타났다.
* 숨김과 복원을 반복해도 정상 동작했고, tray `종료`를 선택하면 process와 overlay, icon이 모두 사라졌다.

## Windows 자동 시작·관리자 권한·단일 실행

### 오늘 목표

MutePilot을 Windows 로그인 때 창 없이 tray에서 시작하고, 관리자 권한 게임의 단독 F키가 필요할 때 사용자가 권한 상태를 확인하거나 정상 UAC를 거쳐 다시 시작할 수 있게 한다. 자동 시작과 수동 실행이 겹쳐도 tray, hotkey, overlay가 중복되지 않게 한다.

### 구현한 내용

* 메인 화면에 `Windows 시작 시 실행`, 현재 권한, `관리자 권한으로 다시 시작`을 묶은 작은 설정 영역을 추가했다. 관리자 게임에서 단독 F키를 사용하려면 MutePilot도 같은 권한이 필요할 수 있다는 설명을 함께 표시한다.
* 현재 권한은 `WindowsIdentity`와 `WindowsPrincipal.IsInRole(Administrator)`로 확인한다. 사용자 이름이나 파일 접근 성공 여부로 추측하지 않는다.
* 자동 시작은 시작프로그램 shortcut이나 `HKCU Run` 대신 Windows Task Scheduler COM API를 사용했다. 작업 이름은 `MutePilot Startup`이다.
* 작업은 현재 사용자 SID의 logon trigger와 `InteractiveToken`, `Highest` run level을 사용한다. SYSTEM 계정, password, 저장된 credential은 사용하지 않는다.
* Task action의 `Path`에는 `Environment.ProcessPath`, `Arguments`에는 `--background`를 각각 넣었다. 경로에 공백이 있어도 command 문자열을 직접 이어 붙이지 않는다.
* 시작 작업 ON/OFF는 같은 MutePilot 실행 파일의 `--startup-task Enable` 또는 `Disable` helper mode를 `runas`로 시작한다. Helper는 tray와 hotkey를 만들지 않고 작업만 변경한 뒤 종료한다.
* 사용자가 UAC를 취소하면 Win32 error 1223을 구분해 기존 instance를 유지하고 실제 task 상태를 다시 읽는다. UI는 JSON 값을 믿지 않고 Task Scheduler의 존재 여부, 현재 실행 경로, background argument, 권한과 사용자 조건을 확인한다.
* `--background`로 시작하면 `MainWindow` handle과 모든 service를 초기화하되 창은 표시하지 않는다. Tray에서 열기를 선택하면 처음 만든 같은 window를 보여 준다.
* 사용자 SID와 Windows session ID를 포함한 `Local\\MutePilot.SingleInstance...` named Mutex를 service 생성 전에 확보한다. 두 번째 일반 실행은 안내 후 종료하고, background 중복 실행은 알림 없이 종료한다.
* 관리자 재실행은 새 process에 `--elevated-restart`와 임시 GUID를 전달한다. 새 process는 최대 20초 동안 기존 Mutex 해제를 기다리고, `runas`가 실제 process를 만든 경우에만 기존 instance가 정상 shutdown한다. UAC가 취소되면 기존 process가 Mutex를 계속 소유한다.
* 실제 종료는 기존 hotkey, polling, fullscreen monitor, overlay와 NotifyIcon을 먼저 정리한 뒤 `App.OnExit`에서 Mutex를 해제한다. 종료하면서 audio mute 상태는 바꾸지 않는다.

### 배운 점

자동 시작 여부를 `settings.json`에 따로 저장하면 실제 Windows task가 지워졌거나 경로가 바뀌었을 때 UI와 시스템 상태가 달라질 수 있다. Task Scheduler를 직접 조회한 결과를 기준으로 ON/OFF를 표시해야 한다.

관리자 권한이 필요한 자동 시작은 일반 startup folder보다 Scheduled Task가 맞지만, `Highest` 작업 생성·제거 자체에는 정상 UAC 승인이 필요하다. 이 승인을 우회하지 않고 helper process만 잠깐 elevated로 실행하면 평소 MutePilot은 일반 권한으로 사용할 수 있다.

Named Mutex는 새 process가 service를 만들기 전에 확인해야 duplicate tray와 hotkey 충돌을 막을 수 있다. 관리자 재실행에서는 새 process가 즉시 포기하지 않고 기존 instance가 안전하게 정리될 시간을 주는 별도 handoff 경로가 필요했다.

### 문제와 해결

Task Scheduler에서 없는 작업을 조회하거나 삭제했을 때 dynamic COM 호출은 `COMException` 대신 같은 HRESULT의 `FileNotFoundException`을 반환했다. Exception type에 의존하지 않고 `0x80070002`, `0x8004130F` HRESULT를 확인해 실제 OFF 상태로 처리했다.

처음 Debug 빌드에서는 이전 수동 테스트용 관리자 MutePilot이 실행 파일을 사용 중이라 apphost 복사가 실패했다. 해당 process를 강제 종료하지 않고 Release build로 compile을 먼저 확인했고, 사용자가 실행한 process가 끝난 뒤 기본 Debug restore/build를 다시 실행했다.

현재 일반 권한 shell에서는 `Highest` task뿐 아니라 제한된 임시 task 생성도 Windows가 access denied로 막았다. UAC를 자동 승인하거나 secure desktop을 조작하지 않았고, `MutePilot Startup` 작업이 생성되지 않은 OFF 상태를 확인했다.

### 확인 결과

* `dotnet restore MutePilot.sln`: 성공
* `dotnet build MutePilot.sln`: 성공, 경고 0개, 오류 0개
* 실제 GUI에서 startup OFF, `현재 권한: 일반 권한`, 관리자 재실행 버튼과 설명이 올바르게 표시됐다. 1024px 높이 화면에서도 footer까지 잘리지 않았다.
* Task Scheduler query는 `MutePilot Startup`이 없는 실제 상태를 OFF로 반환했다. 없는 작업을 `Disable` helper로 처리하면 오류 없이 exit code 0으로 끝났다.
* 일반 권한에서 task 생성은 access denied와 exit code 1로 실패했고 실제 task가 생기지 않았다. UI가 ON이라고 가정하는 별도 JSON 값은 추가하지 않았다.
* `--background` 실행에서 숨겨진 `MainWindow` 한 개와 NotifyIcon 한 개가 만들어졌고 메인 창은 표시되지 않았다.
* 기존 `overlayEnabled`가 OFF이면 background 시작에서도 HUD가 없었다. ON으로 바꿔 재실행했을 때 저장된 HUD가 나타났고, 확인 뒤 tray에서 다시 OFF로 원래 설정을 복구했다.
* Background 중복 실행은 조용히 exit code 0으로 끝났고 process가 하나만 남았다.
* 일반 중복 실행은 `MutePilot이 이미 실행 중입니다. 시스템 트레이를 확인하세요.`를 표시한 뒤 종료했다. 첫 instance의 tray와 service는 그대로 유지됐다.
* `--elevated-restart` handoff를 일반 권한 process 두 개로 재현했다. 새 process는 기존 Mutex가 풀릴 때까지 tray를 만들지 않고 기다렸고, 기존 instance의 정상 종료 뒤 같은 경로를 이어받아 process와 tray가 각각 하나만 남았다.
* `--background`에서 tray icon double-click으로 처음 만든 동일 `MainWindow` handle을 복원했다.
* 실제 UAC 승인을 거친 관리자 권한 재시작이 정상 동작했다.
* `Highest` 자동 시작 작업을 켠 뒤 Windows를 재부팅하고 로그인했을 때 MutePilot이 관리자 권한의 background/tray 상태로 자동 실행됐다.
* 자동 시작된 관리자 권한 MutePilot에서 SuddenAttack 음소거와 볼륨 프리셋 단축키가 정상 동작했다.
* 테스트 뒤 `MutePilot Startup` 작업과 MutePilot process는 남아 있지 않다.

## Master·앱별 볼륨 프리셋 단축키

### 오늘 목표

기존 대상별 음소거 단축키를 그대로 유지하면서 Master Audio와 각 앱에 정확한 볼륨 값을 적용하는 두 번째 단축키를 추가한다. 자동 시작과 관리자 권한 기능은 아직 `main`에 합치지 않고 v0.4 위에 v0.5 브랜치를 쌓아 작업한다.

### 구현한 내용

* 기존에는 hotkey binding 하나가 곧 대상 하나였기 때문에 같은 앱에 두 action을 등록할 수 없었다. `HotkeyActionType.ToggleMute`와 `HotkeyActionType.SetVolumePreset`을 추가하고 `master:mute`, `master:volume`, `application:SUDDENATTACK:mute`, `application:SUDDENATTACK:volume`처럼 binding identity와 target identity를 분리했다.
* Master Audio와 앱별 설정에 1~100% slider, 볼륨 단축키 설정·변경·삭제, `적용` 버튼을 추가했다. 기본 프리셋은 50%다.
* 볼륨 프리셋은 증감이나 두 값 사이의 toggle이 아니다. F1을 mute, F2를 preset으로 설정했다면 F1은 음소거를 전환하고 F2는 매번 저장된 퍼센트로 맞추면서 음소거를 해제한다.
* Master Audio는 기본 playback endpoint의 `MasterVolumeLevelScalar`를 읽고 쓴다. 앱은 기존 `ProcessName` 그룹의 모든 활성 session에서 `SimpleAudioVolume.Volume`을 같은 scalar로 설정하고 `Mute`를 false로 바꾼다.
* 같은 앱의 여러 session 볼륨이 다르면 목록에 `현재 볼륨: 혼합`으로 표시한다. 프리셋 적용 뒤에는 모든 session을 같은 값으로 맞춘 결과를 다시 조회한다.
* 기존 JSON의 `MasterHotkey`와 `ApplicationBindings[].Hotkey`는 계속 mute action으로 사용한다. `MasterVolumeHotkey`, `MasterVolumePercent`, `VolumeHotkey`, `VolumePercent`만 선택적으로 추가했고 누락된 값은 50%와 미설정 상태로 처리한다.
* HUD snapshot에 현재 볼륨과 mixed 여부를 포함했다. 음소거 해제 상태는 `🔊 50%`, 음소거 상태는 `🔇 50%`처럼 표시한다.
* 단축키 입력 창은 하나만 유지하고 호출자가 `음소거 단축키 설정` 또는 `볼륨 단축키 설정` 문맥을 전달하도록 바꿨다.
* 기존 `Windows 시작` 제목은 `실행 설정`, toggle 설명은 `Windows 로그인 시 MutePilot 자동 실행`, 권한 표시는 `현재 실행 권한`, 버튼은 정확히 `MutePilot을 관리자 권한으로 재시작`으로 수정했다.

### 배운 점

대상과 action을 같은 ID로 취급하면 대상 하나에 기능을 하나만 연결할 수 있다. 실제 오디오 대상은 같더라도 등록·교체·삭제해야 하는 binding은 action마다 별도 ID를 가져야 충돌 검사와 설정 rollback이 단순해진다.

볼륨 slider 값은 설정일 뿐 실제 audio state가 아니다. Slider 이동이나 기존 설정 load에서는 Windows audio API를 호출하지 않고, 사용자가 `적용`을 누르거나 볼륨 단축키를 실행한 경우에만 실제 볼륨과 mute 상태를 바꾸도록 경계를 나눴다.

### 문제와 해결

앱별 slider가 ItemsControl에 만들어질 때 발생하는 초기 `ValueChanged`를 사용자 편집으로 잘못 처리하면 앱 감지만으로 설정 파일이 바뀔 수 있었다. Slider가 실제 mouse capture 또는 keyboard focus를 가진 경우만 저장해 초기 binding과 목록 refresh는 무시했다.

여러 audio session 검증용으로 한 process 안에 output 두 개를 만들었을 때 Windows가 하나의 session으로 합쳤다. 같은 `pwsh` process 이름을 가진 무음 output process 두 개를 실행해 서로 다른 20%와 80%를 설정한 뒤, `ProcessName` 그룹이 두 session을 함께 30%로 맞추는 경로를 확인했다.

### 확인 결과

* `dotnet restore MutePilot.sln`: 성공
* `dotnet build MutePilot.sln`: 성공, 경고 0개, 오류 0개
* 기존 형식의 실제 `settings.json`을 시작 전후 SHA-256으로 비교했다. 앱 시작만으로 파일이 다시 저장되지 않았고 기존 `suddenattack` F1 mute binding과 overlay 설정이 그대로 로드됐다.
* 기존 파일에서 Master와 앱 volume hotkey는 미설정, preset은 50%로 표시됐다.
* Master slider를 51%, 저장 앱 slider를 25%로 바꿨을 때 새 필드가 저장됐지만 실제 Master volume은 바뀌지 않았다. 확인 뒤 설정 파일을 원래 byte와 hash로 복구했다.
* Master `50% 적용`은 현재 50%·음소거 해제 상태를 그대로 유지했다.
* 무음 `pwsh` audio session에서 앱 `적용`을 눌러 100%에서 50%로 변경되는 것을 확인하고 100%로 복구했다.
* 같은 무음 session을 먼저 음소거한 뒤 `적용`을 누르자 50%가 설정되고 음소거가 해제됐다.
* 같은 process 이름의 무음 session 두 개를 20%와 80%로 만든 뒤 조회하면 `mixed=true`, 평균 표시 50%였고, 30% preset 적용 뒤 두 session 모두 30%·음소거 해제 상태가 됐다.
* 기존 앱 mute F1이 등록된 상태에서 Master volume F2를 별도 action으로 등록할 수 있었다. Master volume에 F1을 지정하려는 시도는 `이미 MutePilot에서 사용 중인 단축키입니다.`로 거부됐고 기존 F1은 유지됐다.
* HUD에서 Master가 `🔊 50%`, 실행 중이 아닌 `suddenattack`이 `실행 안 됨`으로 표시됐다.
* X를 누르면 process와 HUD가 남았고 tray icon double-click으로 기존 창을 복원했다. Tray `종료` 뒤 process가 정상 종료됐다.
* `--background`는 MainWindow를 표시하지 않고 HUD와 tray icon 한 개를 만들었다. 두 번째 background 실행은 exit code 0으로 끝났고 첫 process만 남았다.
* 검증용 무음 process와 MutePilot process는 모두 종료했고 실제 사용자 audio와 설정 파일을 원래 상태로 복구했다.
* 실제 SuddenAttack에서 mute hotkey와 volume preset hotkey를 함께 사용했고 두 동작이 정상 작동했다.
* 실제 UAC 승인, 관리자 권한 재시작, `Highest` 자동 시작, Windows 재부팅·로그인 뒤 background/tray 실행까지 확인했다.

## 볼륨 프리셋과 원래 소리 상태 전환

### 오늘 목표

v0.5에서 단축키를 누를 때마다 저장한 볼륨을 고정 적용하던 동작을 바꾼다. 첫 동작에서는 프리셋 직전의 실제 볼륨과 음소거 상태를 기억하고, 두 번째 동작에서는 그 상태로 정확히 돌아가게 한다.

### 구현한 내용

* `AudioService`는 Windows 기본 playback endpoint의 장치 ID, 정확한 scalar 볼륨, 음소거 상태를 읽고 복원한다.
* 앱별로는 `ProcessName`에 해당하는 현재 session을 찾고 `GetSessionInstanceIdentifier`로 얻은 runtime identity, PID, 정확한 scalar 볼륨, 음소거 상태를 session마다 기록한다. 프리셋은 현재 session 전체에 같은 값을 적용하고 음소거를 해제하지만, 복원은 각 session이 원래 갖고 있던 값을 따로 사용한다.
* `VolumePresetToggleService`를 추가해 Master와 앱별 기본 상태, 프리셋 활성 여부, 오래된 상태의 무효화를 UI 밖에서 관리한다. 기본 상태는 `settings.json`에 넣지 않고 현재 MutePilot process의 메모리에만 둔다.
* 프리셋 적용이 실패하면 가능한 경우 즉시 원래 상태로 되돌리고 활성 상태로 표시하지 않는다. 복원이 일부 실패하면 기본 상태를 지우지 않아 사용자가 다시 시도할 수 있게 했다.
* 기본 playback endpoint가 바뀌면 이전 Master 상태를 버린다. 앱의 session이 사라지거나 runtime session identity 집합이 달라지면 이전 앱 상태를 새 실행에 복원하지 않고 비활성으로 바꾼다. 주기 조회는 오버레이가 OFF여도 이 검사를 계속한다.
* 수동 버튼과 볼륨 단축키를 같은 toggle service에 연결했다. 버튼은 평소 `10%로 전환`, 활성 중에는 `기본 볼륨으로 복원`처럼 표시한다.
* Slider 이동은 프리셋 숫자만 저장한다. 활성 주기의 기본 상태와 실제 Windows 오디오는 바꾸지 않으며, 먼저 원래 상태를 복원한 다음 새 주기부터 변경한 프리셋을 사용한다.
* 메인 화면에 `기본 볼륨은 프리셋을 적용하기 직전의 소리 상태입니다.`라는 설명을 추가했다. 이 값이 영구 설정처럼 보이지 않게 했다.
* 메인 창을 X로 숨겨도 같은 `MainWindow`와 service가 살아 있으므로 기본 상태가 유지된다. 트레이의 실제 종료로 `OnClosed`가 실행될 때만 service 상태를 비우고, 다음 실행에서는 현재 오디오를 새로 읽는다.

### 배운 점

`ProcessName`은 사용자가 저장하는 대상 이름으로는 알맞지만 실행 중 session을 정확히 구분하기에는 부족하다. 같은 이름의 새 process가 시작됐을 때 예전 값을 덮어쓰지 않으려면 Windows audio session의 runtime identity를 함께 비교해야 한다.

여러 session을 평균 볼륨 하나로만 저장하면 프리셋 해제 뒤 원래 상태를 되살릴 수 없다. UI에는 평균이나 `혼합`으로 보여 주더라도 복원용 상태에는 각 session의 scalar와 mute를 그대로 보관해야 한다.

기본 볼륨은 사용자 설정이 아니라 한 번의 프리셋 사용 주기에 속한 임시 상태다. JSON에 저장하면 재실행한 앱이나 바뀐 장치에 오래된 값을 적용할 수 있으므로 process 수명 안에서만 유지하는 편이 안전하다.

### 문제와 해결

처음에는 앱을 PID 기준으로만 구분하는 방법도 검토했지만 PID는 재사용될 수 있고 같은 앱이 여러 audio session을 가질 수 있다. NAudio의 `GetSessionInstanceIdentifier`를 사용해 현재 session 집합이 그대로인지 먼저 확인하고, 하나라도 달라지면 복원 대신 기본 상태를 폐기하도록 정리했다.

프리셋 활성 중 F1 음소거를 사용하면 현재 mute 상태는 바뀌지만 복원용 기본 상태까지 지우면 안 된다. 음소거 action은 기존 경로를 유지하고 프리셋 service의 상태를 만지지 않게 해 F2가 처음 기록한 볼륨과 mute를 계속 복원하도록 했다.

오버레이가 OFF일 때 주기 조회를 건너뛰면 종료된 앱의 버튼이 한동안 복원 상태로 남을 수 있었다. 오디오 session과 오래된 기본 상태 검사는 계속 수행하고, HUD 표시만 기존 ON/OFF 설정에 맡기도록 바꿨다.

## 사용자가 직접 고르는 단축키

### 오늘 목표

단독 단축키를 F1~F11로 제한하던 애플리케이션 정책을 없앤다. 특정 키를 하나씩 허용 목록에 더하지 않고, 입력 창에서 사용자가 실제로 누른 키를 Windows가 표현할 수 있는 범위에서 그대로 바인딩한다.

### 구현한 내용

* `HotkeyGesture`의 정체성을 WPF `Key`와 표시 문자열이 아닌 `VirtualKey + HotkeyModifiers`로 바꿨다. 화면에 보이는 이름은 이 값에서 별도로 만든다.
* `HotkeyCaptureWindow`는 `PreviewKeyDown`에서 `SystemKey`, `ImeProcessedKey`, `DeadCharProcessedKey`를 포함한 실제 WPF key를 정리하고 `KeyInterop.VirtualKeyFromKey`로 변환한다. 함수 키·문자·숫자를 구분하는 허용 목록은 두지 않았다.
* 입력 안내를 `원하는 단축키를 누르세요.`로 바꾸고 설정한 키의 원래 입력도 다른 프로그램에 그대로 전달된다는 설명을 넣었다.
* Escape를 취소 전용으로 처리하던 분기를 제거했다. Escape도 일반 단축키로 캡처할 수 있고 창을 닫을 때는 기존 `취소` 버튼을 사용한다.
* Modifier가 없는 gesture는 모두 기존 `GetAsyncKeyState` 경로를 사용한다. 약 15ms 간격의 polling task 하나가 현재 등록된 virtual-key dictionary만 순회하며 전체 키보드를 스캔하지 않는다.
* Modifier 조합은 기존 `RegisterHotKey`와 `WM_HOTKEY`를 유지했다. Windows modifier flag도 같은 generic 표현에 포함했고 실제 등록 실패 시 Windows 또는 다른 프로그램에서 사용 중이라는 한국어 안내를 반환한다.
* 순수 Ctrl, Alt, Shift, Win처럼 현재 action 구조에서 대상 키가 모호한 입력은 `이 키는 단독 단축키로 사용할 수 없습니다.`라고 거부한다. 이는 키 종류에 대한 취향이 아니라 등록 방식의 기술적 제한이다.
* 기존 JSON의 `key` 필드를 읽어 virtual-key로 변환하는 converter를 추가했다. 새로 저장할 때는 `virtualKey`를 쓰지만 앱 시작만으로 기존 파일을 다시 저장하지 않는다.
* 바인딩 비교는 normalized modifier flags와 virtual-key record 값으로 한다. 표시 이름이 같아 보이는지를 비교하지 않는다.

### 배운 점

단축키 입력 창이 정상 키를 이미 받고 있어도 검증 단계에서 F키·문자·숫자 범주를 다시 검사하면 실제 기능은 whitelist에 묶인다. Windows가 제공한 virtual-key를 안정적으로 왕복 변환할 수 있는지와 순수 modifier인지 여부만 확인하면 새로운 키 종류를 계속 추가할 필요가 없다.

Standalone polling은 모든 virtual-key를 훑을 이유가 없다. 바인딩 dictionary의 key만 조회하면 사용자가 선택하지 않은 입력은 읽지 않으면서 기존 UP→DOWN latch와 repeat prevention을 그대로 재사용할 수 있다.

### 문제와 해결

기존 설정은 `{"modifiers":"none","key":"f8"}`처럼 WPF enum 이름을 저장했다. 속성을 바로 삭제하면 사용자가 모든 단축키를 다시 만들어야 하므로 전용 JSON converter가 이전 `key`와 새 `virtualKey`를 모두 읽고, 메모리에서는 하나의 virtual-key 형태로 정규화하게 했다.

바인딩을 다른 단독 키로 바꿀 때 이전 key-down latch가 남으면 새 설정과 관계없는 상태가 유지될 수 있다. 기존 registration map을 제거할 때 virtual-key와 latch를 함께 지우고 새로 설정된 키의 현재 down 상태만 초기화하도록 유지했다.

### 확인 결과

* `dotnet restore MutePilot.sln`: 성공
* `dotnet build MutePilot.sln`: 성공, 경고 0개, 오류 0개
* W, S, Space, Escape와 Ctrl+Q가 개별 예외 코드 없이 generic gesture로 만들어지고 검증되는 것을 확인했다.
* 순수 Ctrl virtual-key는 명확한 기술적 제한 메시지와 함께 거부됐다.
* W 단독 바인딩 하나를 등록했을 때 polling map에는 해당 virtual-key 하나만 들어갔다. 같은 W를 다른 action에 등록하면 기존 한국어 중복 메시지로 거부됐다.
* W를 S로 변경하자 W registration과 인위적으로 넣어 확인한 오래된 latch가 제거되고 S 하나만 남았다. S 바인딩을 삭제하자 polling map과 latch가 모두 비었다.
* 변경·삭제 과정에서 처음 만들어진 polling task instance가 그대로 유지돼 shared loop가 추가로 생기지 않았다.
* Ctrl+Alt+Shift+F11 검증 조합이 실제 `RegisterHotKey` map에 등록되고 정상 해제됐다. 이 조합을 사용자용 권장 키로 정한 것은 아니다.
* 기존 F8 JSON을 읽으면 virtual-key 119와 표시 `F8`로 복원됐고, 새 Ctrl+Q gesture는 `{"modifiers":"control","virtualKey":81}` 형태로 직렬화됐다.
* 실제 기존 `settings.json`의 F1/F2가 virtual-key 112/113으로 경고 없이 로드됐다. 직접 load와 GUI 실행 전후 파일 SHA-256이 바뀌지 않았다.
* 실제 GUI에서 기존 F1/F2 표시, 볼륨 toggle 설명, tray hide, overlay·startup·관리자 권한 UI와 `Made by 유성우`를 다시 확인했다.
* 키보드 hook, Raw Input, 입력 기록, 입력 차단, `SendInput`이나 게임 주입은 추가하지 않았다.
* 사용자가 새로 선택한 일반 키가 SuddenAttack에서 Mute 또는 Volume Toggle을 실행하고 게임의 원래 입력도 유지하는지는 아직 수동 검증하지 않았다.
